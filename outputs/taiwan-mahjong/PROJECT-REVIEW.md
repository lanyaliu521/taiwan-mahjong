## 4. 已有功能與使用流程

### 4.1 正式對戰

新一將或繼續存檔 → 發牌與補花 → 摸打及吃碰槓胡回應 → 結算彈窗 → 真人選擇下一局 → 完成一將。真人待答不被電腦或動畫跳過，可暫停與調整自動流程速度。

單擊選牌看預覽、快速雙擊同牌出牌；鍵盤Tab選牌、Enter／空白出牌。合法吃碰槓胡由引擎提供；134遇上家2的13／34吃法已有指定回歸案例。傳統牌面、中央牌河、結算彈窗與提示排版曾依試玩回饋修正。

胡牌結算逐項顯示既有計台結果，含熟悉的牌型名稱、正花及各自台數；紅中、發財、白板分列。呈現層不另算分，避免顯示與實際收付不同。

### 4.2 純練習

136張一般牌、不放回，初始16張加摸1張。選牌預覽 → 捨牌與回饋 → 主動摸下一張；完成或耗盡後換題／同題重練。沒有對手、花牌、吃碰槓或計台，不能當完整對戰的防守訓練。

可看向聽、有效進張、下一張改善比例與一種示例拆法。同題重練沿用原始牌序，獨立保存，不覆蓋對戰。

### 4.3 教練與教學

對戰教練比較合法捨牌及吃碰後合法出牌的牌效，提示可收合／關閉。公開有效牌比例不是實際牌牆摸牌率；向聽是結構下限，不是還要幾回合；示例拆法不保證最大搭數。

六步新手教學可從首頁、對戰或練習進入，含獨立出牌與兩種吃法示範。示範不改正式牌局；對戰開啟教學先暫停，關閉後由玩家繼續。

### 4.4 正向回饋與資料保護

已提供牌效進步、聽牌、吃碰成立、實際胡牌得分與練習鼓勵。這些是事件／牌效回饋，不代表已有完整成就、任務或成長系統。

保存失敗保留進度並提供重試；跨分頁衝突停止操作，避免覆蓋。結算只付款一次，重開彈窗或重載不重付。資料依網站來源與瀏覽器保存，換域名／連接埠／瀏覽器不會自動搬移。

## 5. 桌規與不可默默改動的界線

唯一正式版本：[TW16-CLASSIC-v1完整規則與台表](../taiwan-mahjong-m0/RULES.md)。下列為審查摘要，不取代完整花胡矩陣、過水、禁捨及互斥台表。

- 144張含8花，通常待進牌16張、待出牌17張；一般胡牌為五面子加一對，槓在結構上算一面子。
- 無日麻振聽、役門檻、七對、十三么或八對半；零台可以胡。
- 回應先胡、再碰／明槓、最後下家吃；多家胡按規定座序攔胡，不按回應速度。
- 有吃碰禁捨、回吃碰、過碰、過水；明槓來源與槓後行為依本案固定規則。
- 牌尾固定保留16張；補花、槓與尾局共用抽牌邊界；花胡有獨立事件規則。
- 底30、每台10，可負分、無封頂；莊連台依付款對象計，不直接加在無關閒家交易上。
- **莊胡或流局都續莊且連莊數增加；閒家胡才移莊。** 16次移莊完成一將，末莊仍可能續局。

更改桌規是產品規格變更，須命名新版本、補案例並處理舊存檔，不以美術或AI優化名義順手更改。

## 6. 正式AI與人性化AI的實際差距

### 6.1 現行策略

`src/ai.ts`只接自家可見資訊及合法動作，合法WIN優先。主要比較一步牌效的向聽及公開有效進張；吃碰會看其後合法捨牌，同效時稍偏門清；槓有簡化加分，尚無搶槓風險估計。平手使用可保存的亂數選擇。

目前不是完整攻守AI，三位電腦沒有已上線的個性軸，也沒有校準的放槍率、牌型價值期望或阻莊長期收益模型。遊戲AI是本機程式，不呼叫Sol、Luna或其他語言模型。

### 6.2 已完成的設計

四軸：冒險容忍、副露偏好、價值企圖、調整意願；共用能力與資訊，藉取捨差異形成牌風。預計有偏快速門清、積極副露、謹慎調整的三種方向，數值尚待校準。

留安全張可代表保留退路、最後安全進聽等用途；不能把特定習慣直接等同年齡或性格。所謂欺敵效果目前沒有驗證，不先給虛構收益。不靠作弊、餵牌、任意拒胡或亂數失誤製造人性。

### 6.3 已完成的離線程式

| 模組 | 已做到 | 尚未做到 |
|---|---|---|
| `safety.ts` | 依公開容量排除普通放槍的將、刻、順子成形路徑，提供充分安全證明 | 未校準放槍概率，不涵蓋整局安全 |
| `risk-evidence.ts` | 對手別／全桌安全、持有與合法可捨安全庫存、條件式付款底線 | 未知牌的危險排序、完整威脅推估 |
| `strategy-comparison.ts` | 合法WIN優先、向聽損失門檻、對莊／對閒未知證據權重、平手候選比較 | 自動切換、對局強度、正式人格及保存整合 |

有留安全張的3組牌例、公開容量見證及對莊偏好的4組消融；這些是局部證據，不是新人格已完成對局驗收。

### 6.4 「不讓莊家連莊」如何納入

此為使用者新強調的目標，須與本局直接損失、自身胡牌速度共同考量。退守避免放槍卻可能促成流局續莊，不能將「沒有放槍給莊」當唯一成功指標。

最近牌例：三萬可保持聽牌且只對莊有安全證明；一筒對三家有證明但退出聽牌。實驗顯示牌效門檻影響結果，**尚未證明單獨提高莊權重改善策略**。權重只是偏好，未知不等於危險，不能說成放槍概率。自己當莊須採自身目標，不把自己當敵對莊家。

若繼續實作，先補對莊／對閒安全衝突與同向聽有效進張損失，再用同種子換座對局分開量測：放槍給莊、莊自摸、流局續莊、自家胡、其他閒家胡及總點數。正式人格與進度保存另設驗收。

## 7. 技術架構與修改地圖

TypeScript、Vite、原生HTML／CSS及瀏覽器儲存；目前沒有執行時套件或後端。開發依賴依package-lock鎖定，部署工作流程使用Node 24.12.0。

資料流：畫面送命令 → main檢查畫面代次 → session推進 → engine驗合法與版本 → 新狀態保存 → 重繪。AI／教練只讀getObservation；引擎是合法動作唯一來源。

| 職責 | 主要檔案 |

| 狀態、規則、牌權與還原 | `src/model.ts`、`engine.ts`、`validation.ts` |
| 牌、胡牌結構、計台收付 | `tiles.ts`、`hand.ts`、`scoring.ts` |
| 共用牌效、正式電腦 | `analysis.ts`、`ai.ts` |
| 排程、續局、事件整合 | `session.ts`、`main.ts` |
| 對戰畫面、牌面與排版 | `view.ts`、`tile-face.ts`、`style.css` |
| 練習、教練、教學、回饋 | `practice.ts`、`practice-view.ts`、`coach.ts`、`tutorial-view.ts`、`feedback.ts` |

實際型別以程式為準，[CONTRACTS](../taiwan-mahjong-m0/CONTRACTS.md)是概念契約。不要為未來玩法先造通用框架；先由具體需求決定最小改動。

## 8. 存檔、相容性與公平

| 資料 | 本機鍵／版本 | 擴充注意 |
|---|---|---|
| 對戰 | `tw16:TW16-CLASSIC-v1:save`；Session／GameState版本1 | 含3位AI亂數；新個性或模式記憶須設計遷移 |
| 練習 | `tw16:practice:v1`；版本1 | 由種子與捨牌日誌重播驗證；改演算法須評估相容 |
| 教練偏好 | `tw16:coach:v1` | 與牌局分離 |

還原必須走decodeSession及引擎restore，不能只JSON.parse；未知版本、壞檔、非法牌權須拒絕並保留原資料。不可把清空儲存當修復。跨裝置／網址搬移目前沒有匯入匯出流程。

AI、教練、研究策略只接指定玩家觀察；對手暗槓只可知有該面子，不可知道牌種。不能在提示或角色介紹洩漏對手即時聽口、真實向聽或私人模式。

## 9. 品質、已知限制與維護負擔

278項測試涵蓋規則、計台、存檔、控制器、AI／教練、練習及離線研究。歷史另有桌面／320與390寬的瀏覽器驗收、完整牌局模擬。測試通過不等於所有裝置皆驗過，窄視窗不等於手機實機或Safari驗證。

| 限制／負擔 | 影響與處理方向 |
|---|---|
| AI以一步牌效為主 | 不宣稱成熟攻守；研究另行驗收後才接正式策略 |
| 人性化成果多為局部證據 | 先定評估指標，避免持續擴充研究但無可審查版本 |
| 提示數學容易誤解 | 保留向聽、公開比例與實際概率區別，依新手試玩調文字 |
| 文件歷史較多 | README／HANDOFF為入口；本文件供整體審查，歷史報告只作證據 |
| 顯示／操作曾反覆修正 | 新UI工作須重驗牌桌空間、焦點、結算、展開提示與窄畫面 |
| 本機存檔綁來源 | 若需要備份／跨裝置，先定資料格式與安全匯入再開發 |
| 單一整合控制器承擔多模式 | 先按實際修改困難小幅整理，不為美觀整包重寫 |
| 遠端落後本機一個研究包 | 明確記錄，推送後才核對新CI，不混淆已發布狀態 |

本次不是重新進行全專案安全／效能／所有裝置稽核；是核對現有實作與證據，整理可決策的完整狀態。

## 10. 建議重新決定的目標

以下尚未選定，不在本次自動開工。

| 決策 | 可選方向 | 對後續工作的影響 |
|---|---|---|
| 核心價值 | 輕鬆陪打／學習牌效／可信的人性化對手 | 決定下一個主要里程碑 |
| 遊戲回饋 | 小幅聲畫與事件回饋／完整任務成長 | 後者涉及新狀態、保存與較大UI成本 |
| AI首版目標 | 基本攻守／可辨個性／較高強度 | 不應一次把三者都列為首版必要條件 |
| 阻莊優先程度 | 作為局況偏好／較高但有限代價／主要勝負目標 | 需說清是否容許犧牲自身點數及多少牌效 |
| 桌規 | 保持單一版本／增加可選桌規 | 多桌規大幅擴大測試與相容性負擔 |
| 提示深度 | 預設精簡／教學導向／可調程度 | 影響資訊密度及新手理解成本 |
| 支援平台 | 桌面優先／手機同等優先 | 後者需要實機與不同瀏覽器驗收 |
| 保存需求 | 本機即可／匯出備份／帳號同步 | 成本逐級上升；同步改變純靜態定位 |

建議先選一項主軸及最多一項配套，以可試玩的工作包前進；每包寫清玩家能感受到的變化、完成條件與不包含項目。保留現行站供試玩，不將研究狀態當正式版本承諾。

## 11. 重新定案後的建議順序

1. 確定主體玩家、最重要體驗與下一版範圍；將本底稿中的待決策轉成明確選擇。
2. 整理ROADMAP為新階段與驗收標準，保留過去證據但移除現況歧義。
3. 先修阻礙遊玩的真實問題，再完成一個可試玩的主要工作包。
4. 若選人性化AI：補衝突牌例與評估，再做最小攻守版本；人格、保存遷移與介面依序驗，不一次上全部參數。
5. 通過規則／資料／操作測試後部署；核對指定提交的Actions、正式資源與受影響流程。
6. 以試玩結果調整；每包同步文件與HANDOFF，避免下次重新讀完整對話。
